# Требования к AI-помощнику

## 1. Принципы

AI встроен в карточки, dashboard, контент и базу знаний. Он формирует рекомендацию или черновик, а не создает скрытую параллельную бизнес-логику. Детерминированные правила, права и state machines исполняются приложением вне модели.

| ID | Требование |
|---|---|
| AI-001 | Каждый AI-вызов должен иметь зарегистрированный use case, цель, разрешенные источники, допустимые действия и risk class. |
| AI-002 | AI должен наследовать tenant, row-level и field-level область доступа инициатора; системные batch-сценарии используют минимальный service scope. |
| AI-003 | Рекомендация должна хранить use case, subject, дату, основание, источники/citations, использованные категории данных, confidence, версии модели/prompt/policy и решение пользователя. |
| AI-004 | AI не должен отправлять сообщение, менять критичный статус, регистрировать партнера, оформлять/оплачивать заказ или менять структуру без явного подтверждения или детерминированного утвержденного правила. |
| AI-005 | Пользователь должен принять, отредактировать или отклонить предложение; исправления и причина отклонения используются как контролируемая обратная связь. |
| AI-006 | При недостаточных/противоречивых данных AI должен сообщать ограничение и не заполнять неизвестное вымышленными фактами. |
| AI-007 | AI не должен ставить диагноз, обещать результат, назначать лечение, скрывать противопоказания или генерировать неподтвержденные свойства продукта. |
| AI-008 | Продуктовый ответ должен основываться на approved актуальной tenant knowledge base и содержать ссылку на конкретную версию источника. |
| AI-009 | При адаптации контента AI не должен изменять protected fragments: legal disclaimer, состав, противопоказания, свойства и утверждения производителя. |
| AI-010 | Система должна обнаруживать prompt injection в загруженном/полученном контенте и не считать внешний текст системной инструкцией. |
| AI-011 | PII должна минимизироваться/псевдонимизироваться до передачи провайдеру; провайдер и регион должны соответствовать tenant policy. |
| AI-012 | Должны существовать quota, rate limit, timeout, retry policy, cost telemetry и kill switch по tenant/use case. |
| AI-013 | Ответ AI должен проходить policy filters до показа или действия; блокировка аудируется безопасной причиной. |
| AI-014 | Confidence отображается только если калиброван для use case; иначе используется качественная метка с пояснением. |
| AI-015 | AI не должен показывать скрытую цепочку рассуждений; объяснение состоит из бизнес-факторов и проверяемых источников. |

## 2. Разрешенные MVP-сценарии

| Use case | Вход | Результат | Обязательный контроль |
|---|---|---|---|
| План дня | доступные задачи, SLA, встречи, signals | приоритизированные предложения задач | пользователь подтверждает |
| Резюме контакта | разрешенная timeline | краткие факты, открытые вопросы, next step | ссылки на записи timeline |
| Черновик сообщения | контекст, канал, approved template/content | редактируемый draft | consent check и ручная отправка |
| Поиск по базе знаний | вопрос + approved KB | ответ с citations | отказ без источника |
| Follow-up suggestion | journey, order, feedback | следующий безопасный шаг | policy и подтверждение |
| Weekly report | агрегированные KPI | резюме изменений и факторов | метрики рассчитывает analytics service |

## 3. Перспективные сценарии

Прогноз repeat order, risk of disengagement, weak branches, potential leaders и product matching допускаются после накопления данных, определения target labels, оценки bias/precision/recall и процедуры мониторинга drift. В MVP они рекомендуются как прозрачные rules, а не ML-утверждения.

## 4. Оценка качества

Для каждого use case до production создается eval set без неконтролируемых PII, метрики factuality/citation correctness, policy violations, task success, latency/cost и human acceptance. Изменение модели или prompt требует regression eval и version rollout.
