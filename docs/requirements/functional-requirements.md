# Функциональные требования

## 1. Общие требования

| ID | Требование |
|---|---|
| FR-CORE-001 | Система должна проверять tenant, роль, область структуры, владение объектом и чувствительность поля при каждой операции чтения/изменения. |
| FR-CORE-002 | Система должна сохранять автора, время, источник и correlation ID значимого изменения. |
| FR-CORE-003 | Система должна поддерживать пользовательские поля из типизированного набора с валидацией и правами. |
| FR-CORE-004 | Система должна показывать следующий шаг и его срок на карточках активных процессов. |
| FR-CORE-005 | Массовые операции должны иметь предварительный просмотр, оценку затронутых записей, подтверждение и отчет результата. |
| FR-CORE-006 | Импорт должен поддерживать сопоставление колонок, dry-run, валидацию, частичный успех, файл ошибок и идемпотентный повтор. |
| FR-CORE-007 | Экспорт должен учитывать текущие фильтры, разрешенные поля, маскирование и аудит. |

## 2. Главная страница

| ID | Требование |
|---|---|
| FR-DASH-001 | Система должна показывать показатели дня/недели/месяца: контакты, задачи, встречи, кандидаты, продажи, активных партнеров, повторные заказы и follow-up. |
| FR-DASH-002 | Система должна показывать просроченные задачи, клиентов для касания, партнеров с объяснимым сигналом риска, дни рождения, мероприятия, обучение и прогресс ранга. |
| FR-DASH-003 | Пользователь должен выбирать, скрывать и упорядочивать разрешенные виджеты. |
| FR-DASH-004 | Каждый показатель должен поддерживать переход к отфильтрованной выборке и показывать период/время обновления. |
| FR-DASH-005 | AI-план дня отображается как список предложений; добавление задачи требует выбора/подтверждения пользователя. |

## 3. Контакты

| ID | Требование |
|---|---|
| FR-CONTACT-001 | Система должна создавать Contact вручную, из импорта и через разрешенную интеграцию. |
| FR-CONTACT-002 | Contact должен поддерживать несколько одновременных ContactRole без дублирования общей истории. |
| FR-CONTACT-003 | Карточка должна содержать идентификационные данные, каналы, локаль, источник, отношения, интересы, потребности, мотивацию, возражения, теги, ответственного, наставника, согласия, историю, задачи и файлы. |
| FR-CONTACT-004 | До создания Система должна искать возможные дубли по нормализованным телефону, email, external ID и настраиваемым признакам. |
| FR-CONTACT-005 | Merge должен выбирать survivor, показывать конфликтующие поля, переносить связи, сохранять alias/map и аудит; финансовые записи не объединяются без специального правила. |
| FR-CONTACT-006 | Система должна поддерживать archive, restore, anonymize и delete request как разные операции. |
| FR-CONTACT-007 | Массовое назначение тегов/ответственного должно проверять права для каждой записи и выдавать детальный результат. |
| FR-CONTACT-008 | Поиск должен работать по ФИО, нормализованному каналу, тегам и идентификаторам с учетом маскирования. |

## 4. Воронки рекрутинга и продаж

| ID | Требование |
|---|---|
| FR-FUNNEL-001 | Администратор должен создавать версионируемые Funnel и FunnelStage отдельно по процессам. |
| FR-FUNNEL-002 | Этап должен задавать обязательные поля, допустимые переходы, SLA, причины исхода, задачи, уведомления и шаблоны. |
| FR-FUNNEL-003 | Переход должен быть атомарным: проверить правило, сохранить StageHistory, выполнить синхронные действия и поставить асинхронные действия в очередь. |
| FR-FUNNEL-004 | Повторная команда с тем же idempotency key не должна повторять переход и автоматизации. |
| FR-FUNNEL-005 | Система должна поддерживать Kanban, список и аналитику; недоступные карточки и поля не должны раскрываться агрегатами. |
| FR-FUNNEL-006 | Перемещение drag-and-drop должно запрашивать отсутствующие обязательные данные до завершения. |
| FR-RECRUIT-001 | Базовый шаблон этапов должен включать перечисленные 14 этапов и позволять tenant изменить/деактивировать их. |
| FR-RECRUIT-002 | Отказ должен требовать причину; отложенный интерес — дату следующего допустимого касания. |
| FR-RECRUIT-003 | Регистрация должна проверять уникальность partner external ID и создавать связи по UC-001. |
| FR-SALES-001 | Клиентская воронка должна поддерживать потребность, предложение, заказ, оплату, доставку, получение, follow-up, повторную продажу и отказ. |

## 5. Сетевая структура

| ID | Требование |
|---|---|
| FR-NETWORK-001 | Система должна поддерживать внутренний и внешний master-режим структуры. |
| FR-NETWORK-002 | Дерево должно поддерживать lazy loading, поиск, поколения, ветки, наставников, сворачивание и снимок на дату. |
| FR-NETWORK-003 | Узел должен показывать разрешенные данные: sponsor, mentor, дата вступления, текущий/предыдущий ранг, объемы, активность и риск с факторами. |
| FR-NETWORK-004 | Система должна запрещать цикл, self-sponsorship и более одной активной sponsor-связи партнера. |
| FR-NETWORK-005 | Изменение sponsor/mentor должно быть версионируемым и аудируемым. |
| FR-NETWORK-006 | Фильтры должны включать период, ранг, активность, продажи, обучение, новых, без заказов/действий и потенциальных лидеров. |
| FR-NETWORK-007 | Агрегаты ветки должны показывать дату, источник и статус расчета; длительный пересчет выполняется асинхронно. |

## 6. Продукты и рекомендации

| ID | Требование |
|---|---|
| FR-PRODUCT-001 | Система должна вести категории, продукт, варианты, медиа, состав, характеристики, официальное применение, длительность, хранение, противопоказания, предупреждения, документы и связи. |
| FR-PRODUCT-002 | Цена должна иметь тип, валюту, период действия, сегмент/ранг/регион и приоритет; пересечение правил должно выявляться. |
| FR-PRODUCT-003 | Продукт и документ должны иметь workflow draft → review → approved → retired и версии. |
| FR-PRODUCT-004 | Наличие и остаток должны хранить источник и актуальность; при внешнем master ручное исправление запрещено. |
| FR-REC-001 | Анкета потребности должна быть версионируемой и хранить цель, ограничения, аллергии, бюджет и используемые продукты при наличии законного основания. |
| FR-REC-002 | Рекомендация должна содержать продукты, основание, источник, ограничения, альтернативы и предупреждение. |
| FR-REC-003 | При отсутствии утвержденного источника Система должна отказать в продуктовой AI-рекомендации и предложить обратиться к специалисту/ответственному. |

## 7. Заказы, оплаты, доставка и возвраты

| ID | Требование |
|---|---|
| FR-ORDER-001 | Заказ должен создаваться вручную, из Client, Opportunity, Recommendation, прошлого заказа и подписки. |
| FR-ORDER-002 | Система должна поддерживать снимки цены, скидки, промокода, бонусов, налогов, валюты, количества и названия продукта. |
| FR-ORDER-003 | Базовые статусы: draft, awaiting_confirmation, awaiting_payment, paid, picking, shipped, delivered, received, cancelled, partially_returned, returned. |
| FR-ORDER-004 | Допустимые переходы должны задаваться state machine; невозможный переход возвращает конфликт с текущим состоянием. |
| FR-ORDER-005 | Оплата должна поддерживать одну или несколько транзакций, partial/paid/failed/refunded; webhook обрабатывается идемпотентно. |
| FR-ORDER-006 | Система должна поддерживать delivery/pickup, частичную комплектацию и несколько отправлений как перспективное расширение модели. |
| FR-ORDER-007 | Отмена после оплаты выполняется только разрешенным процессом с возвратом/корректировкой, не удалением. |
| FR-ORDER-008 | Return должен ссылаться на позиции, количество, причину, решение, сумму и платежное возмещение. |
| FR-ORDER-009 | Received должен публиковать OrderReceived/OrderDelivered согласно словарю статусов и запускать follow-up один раз. |
| FR-ORDER-010 | Регулярный заказ/подписка не должен инициировать списание без действующего мандата и уведомления по правилам юрисдикции. |

## 8. Постпродажное сопровождение и повторные продажи

| ID | Требование |
|---|---|
| FR-FOLLOW-001 | Администратор должен настраивать сценарии по продукту, категории, сегменту, стране, языку и каналу с приоритетом правил. |
| FR-FOLLOW-002 | Базовый шаблон должен поддерживать шаги D0, D+1, D+3, D+7, D+14, перед окончанием, после окончания и запрос отзыва. |
| FR-FOLLOW-003 | Экземпляр сценария должен закреплять версию шаблона, ответственного, дату начала, плановые даты, статусы и результаты шагов. |
| FR-FOLLOW-004 | Отсутствие согласия на канал не отменяет внутреннюю задачу, но блокирует внешнее сообщение. |
| FR-FOLLOW-005 | Жалоба/нежелательная реакция должна создавать Case, приостанавливать несовместимые маркетинговые шаги и эскалироваться. |
| FR-REPEAT-001 | Система должна вычислять expected_end_date из количества, стандартной длительности, частоты и даты начала, сохраняя формулу и входы. |
| FR-REPEAT-002 | Пользователь должен иметь возможность скорректировать дату с причиной; расчетное и ручное значение сохраняются отдельно. |
| FR-REPEAT-003 | Сегменты должны включать soon_end, due, overdue, dormant, single_product, high_value, declining_frequency, subscription_candidate и partner_candidate. |
| FR-REPEAT-004 | Предложение повторного заказа создает Task/Notification или draft Order; финальный заказ требует подтверждения. |

|---|---|

| FR-COMM-002 | Полный текст внешнего сообщения хранится только при законном основании и поддержке API; иначе сохраняются метаданные/ручное резюме. |
